# Конфигурация ANPR System

Документ описывает, **где хранится каждое значение, кто им владеет и когда оно применяется**. Источник истины по ключам и дефолтам — `config/registry.py`; таблицы ниже сверяются с реестром тестом `tests/test_config_architecture.py` (каждый ключ реестра обязан быть здесь описан). Историю решений и аудит см. в [`docs/roadmap/configuration-architecture.md`](../roadmap/configuration-architecture.md).

Файла настроек нет. Конфигурация делится на четыре класса; каждое значение относится ровно к одному.

## Классификация конфигурации

| Класс | Название | Хранилище | Кто меняет | Когда загружается | Эффект изменения |
|---|---|---|---|---|---|
| **D** | Развёртывание и инфраструктура | переменные окружения (`.env`, `docker-compose.yml`) | инженер развёртывания | один раз при старте процесса, `EnvConfig` (`config/env_settings.py`) | перезапуск контейнера |
| **A** | Операционные настройки инстанса | таблица `app_settings` (одна строка на ключ) | администратор через UI | при обращении; кэш `SettingsService`, инвалидация по `revision` | сразу либо с автоматическим перезапуском обработчика (`requires_restart`) |
| **C** | Константы кода | код | разработчик | при импорте | релиз |
| **L** | Состояние устройства и личные UI-предпочтения | `localStorage` браузера | сам пользователь этого браузера, неявно | при загрузке страницы | сразу, только на этом устройстве |

Класс C (реестр прав, контракт весов модели, алгоритм JWT, форматы номеров стран `anpr/countries/*.yaml`, домены перечислений) записями реестра не представлен; реестр владеет доменами перечислений и дефолтами ключей класса A. Конфигурация объектов — каналы (`channels`), контроллеры, зоны, списки, пользователи — хранится в собственных таблицах PostgreSQL (в том числе RTSP-адреса в `channels.source` и пароли контроллеров в `controllers.password`, а не в файлах).

Личных серверных предпочтений (`users.preferences`, прежний класс U) в проекте больше нет: тема, стиль, закрепление панели, debug-панель и метрики каналов вернулись на `localStorage` (класс L) — они не должны переезжать между рабочими местами, а будущий технический суперадмин (роадмап, фаза 11) не будет иметь строки в `users` вовсе. Решение и причина — в [`docs/roadmap/configuration-architecture.md`](../roadmap/configuration-architecture.md).

## Правила приоритета

1. **У каждого значения один источник истины.** Остальные слои — либо кэш с явной инвалидацией, либо документированный bootstrap.
2. **Разрешены только две формы многослойности:**
   - операционная настройка поверх кода: `app_settings` → константа реестра;
   - bootstrap до готовности БД: `LOG_LEVEL` (env) действует от старта процесса до первого успешного чтения `logging.level` из `app_settings`, затем владельцем становится БД.
3. **Отсутствие строки в `app_settings` — не ошибка**, а значение из реестра. Поэтому на чистой установке таблица пуста и всё работает.
4. **Класс D никогда не пересекается с классом A** (единственное исключение — bootstrap `LOG_LEVEL`). Пути, DSN, секреты, лимиты пулов, пути к весам — только окружение и через UI не меняются.
5. **Класс L не имеет серверного владельца.** Каждый ключ `localStorage` — состояние конкретного устройства/браузера (тема, стиль, закрепление панели, debug-панель, метрики каналов, размер и порядок видеосетки); нет ни кэша, ни сверки с сервером, ни переноса между рабочими местами. Cookie не используются. Недоступный `localStorage` не ломает приложение — каждый ключ просто откатывается к код-дефолту.
6. **Значение без потребителя запрещено:** ключ либо потребляется кодом, либо помечен `reserved` (сейчас — `interface.default_locale`, слоя локализации нет).
7. **Настройки инстанса (класс A) требуют права `tab:settings`** (переходная схема до пересмотра модели доступа в фазе 11); класс L не проходит через API вообще — авторизация браузера не нужна для его собственного `localStorage`.

## Модель темы и стиля

Тема и стиль — **только состояние этого браузера** (`localStorage`, класс L), без сервера, без учётной записи и без переноса на другое рабочее место. Порядок: сохранённое значение в этом браузере → код-константы `light` / `graphite-minimal`.

| Момент | Что происходит |
|---|---|
| Загрузка страницы | `appearance.boot()` синхронно читает `anpr_theme`/`anpr_style` и применяет их — до проверки токена, до входа, без единого сетевого запроса |
| Переключение темы или стиля | `appearance.set(...)` применяет значение и сразу пишет его в `localStorage`; ничего не может «не сохраниться», нет отката и уведомления об ошибке |
| Выход / вход другого пользователя | ничего не происходит: ключи не привязаны к пользователю, значение остаётся тем же на этом устройстве для следующего вошедшего |
| Нет `localStorage` | приложение работает на код-дефолтах; выбор просто не переживает перезагрузку страницы |

Управление: страница **Мои предпочтения** (тема и стиль; опции `<select>` — статичный HTML, не из `GET /api/settings/schema`) и кнопка темы в верхней панели. Закрепление левой панели, debug-панель и метрики каналов — тем же путём: `localStorage`, без сервера; их управляющие элементы (кнопка в боковой панели, два чекбокса в Настройки → Разработка) описаны в `device-prefs.js`. Реализация темы/стиля: `appearance-core.js` (логика), `appearance.js` (обвязка), `ui.js` только применяет значения к DOM.

## Модель времени

| Слой | Решение |
|---|---|
| Зона ОС контейнера | не влияет ни на что: `TZ=UTC`; `datetime.now()` без зоны и `astimezone()` без аргумента запрещены тестом-инвариантом |
| Хранение | всегда UTC: `TIMESTAMPTZ`, ISO-8601 со смещением |
| Зона инстанса | `app_settings['interface.display_timezone']` (IANA), задаётся в **Настройки → Общие → Время**. Пока администратор её не выбрал, ключа в БД нет |
| Зона клиента | **значение по умолчанию**: пока зона инстанса не выбрана, интерфейс показывает время компьютера пользователя (зона браузера). Личной зоны нет |

`GET /api/system/time` возвращает `display_timezone: null`, пока зона не выбрана явно (выбор даже `UTC` считается явным); тогда клиент форматирует время в собственной зоне. Единственный форматтер на клиенте — `app/web/js/datetime.js` (`Intl.DateTimeFormat`, явные `timeZone` и `ru-RU`); часы топбара показывают серверное время с измеренной поправкой, отрисованное в выбранной зоне; подпись зоны под часами и над журналом выводится только для явно выбранной зоны. Значения `datetime-local` в фильтрах журнала трактуются в зоне отображения и уходят в API как UTC. Экспорт CSV/ZIP форматируется в зоне инстанса (сервер не знает зону клиента; без выбранной зоны — `UTC`), зона указана в заголовках колонок и в имени файла.

## Что делать при добавлении настройки

1. Добавить запись в `config/registry.py` (класс, тип, дефолт, границы или `choices`, `requires_restart`, владелец, описание). Для класса A пользовательские значения пишутся через `SettingsService.update`, читаются через `get`/`get_section`; отдельных аксессоров по секциям нет.
2. Показать в `PUT /api/settings` (класс A); для перечислений добавить домен в `ENUMS` — список для UI отдаёт `GET /api/settings/schema`. Личное UI-состояние без серверного владельца (класс L) через API не идёт вообще — см. `device-prefs.js`/`appearance.js` как образец.
3. Для класса D — переменная в `EnvConfig` и `.env.example`; читать окружение вне `config/env_settings.py` нельзя.
4. Добавить строку в таблицы ниже (тест это проверяет) и, если ключ потребляется, убедиться, что потребитель существует.
