# Web ANPR System — Роли, пользователи и права доступа

## What This Is

Самостоятельно разворачиваемая многоканальная система распознавания автомобильных номеров (ANPR) с веб-интерфейсом, REST API и управлением реле шлагбаумов/ворот. Текущий цикл полностью перерабатывает модель пользователей и прав: администратор создаёт роли с произвольным названием, отмечает галочками доступы по разделам (Просмотр / Изменение / Удаление) и назначает роль любому числу пользователей. Для охранников-операторов и администраторов парковок/КПП.

## Core Value

Администратор может гибко выдать любому пользователю ровно те доступы, которые нужны, через роли с галочками, и сервер реально соблюдает эти права, а не только скрывает вкладки.

### Active

<!-- Гипотезы текущего цикла до выпуска и проверки. -->

- [ ] Сущность «Роль»: произвольное название + набор галочек доступа; роли создаются, редактируются и удаляются через UI
- [ ] Права по разделам с раздельными галочками Просмотр / Изменение / Удаление (Наблюдение, Журнал, Зоны, Клиенты, Настройки)
- [ ] «Настройки» — одна галочка на весь раздел в этом цикле (дробление на подразделы — позже)
- [ ] Сервер применяет права ко всем эндпоинтам (не только скрытие вкладок); видимость вкладки выводится из права «Просмотр»
- [ ] Пользователь: логин, пароль, ФИО, одна роль; одну роль можно назначить многим пользователям
- [ ] Блокировка пользователя без удаления
- [ ] Изменение роли/прав применяется к уже вошедшим пользователям сразу, без перевхода
- [ ] Журнал действий пользователей (кто/когда: открыл шлагбаум, изменил роль, удалил канал и т. п.)
- [ ] При развёртывании в БД создаются пользователи `admin` (роль «Администратор», все права) и `operator` (роль «Оператор», только Наблюдение и Зоны) с паролями по умолчанию; смена пароля не принуждается. Эти роли — обычные, редактируемые, без особой логики
- [ ] superadmin — единственный, кому доступен раздел «Разработка» (dev-инструменты); он нигде не отображается и не отслеживается, через него можно создать первого администратора
- [ ] Ручное срабатывание реле — отдельная галочка «Ручное управление реле»; добавление/изменение/удаление контроллеров — права «Настроек» (решено владельцем после исследования)

### Out of Scope

- Ограничение роли по конкретным каналам/камерам — отложено; в этом цикле роль даёт доступ к разделу целиком
- Дробление «Настроек» на подразделы с отдельными галочками — отложено до исследования работы с контроллерами
- Миграция существующих пользователей и полей `users.role` / `users.permissions` — по политике проекта схема чистая, пользователи пересоздаются
- Несколько ролей на одного пользователя — по формулировке владельца у пользователя одна роль
- Серверные персональные предпочтения — всё личное состояние UI остаётся в `localStorage`
- Принудительная смена пароля по умолчанию — владелец решил не принуждать

## Context

- Brownfield: FastAPI + PostgreSQL 16 + ES-модули фронтенда (`app/web/js/`), контейнер `AppContainer`, Docker Compose on-prem. Карта кода — `.planning/codebase/`.
- Предыдущие шаги (перенос superadmin в env, персональных настроек UI в `localStorage`) делались именно для подготовки этой переработки прав.
- Аудит текущей модели (`docs/roadmap/configuration-architecture.md`, раздел 2.7, P18/P19): бэкенд проверяет только `tab:settings` (18 мест), `tab:obs|journal|clients|zones` на сервере не проверяются нигде, 46 эндпоинтов защищены только фактом входа (включая `DELETE /api/channels/{id}`), `change_password` проверяет `tab:settings` в теле обработчика, контроллеры и debug закрыты `require_role("superadmin")` (11 мест).
- Этот цикл и есть «фаза 11» из `configuration-architecture.md`: авторизация, вкладки и навигация перерабатываются целиком.
- Уровни доступа (`public`, `self`, `admin-*`) через адаптерные зависимости в `app/api/deps.py` были введены как шов, чтобы решение о модели прав принималось один раз и в одном месте.
- Текущая таблица `users`: `login`, `password`, `role` TEXT, `permissions` JSONB, `is_active`, временные метки.

## Constraints

- **Tech stack**: FastAPI, PostgreSQL как единственное хранилище, без Redis — изменения только в рамках существующего стека
- **Схема БД**: прямые изменения в `database/postgres/schema.sql` + inline `_SCHEMA` репозиториев (синхронизацию проверяет `tests/test_schema_sync.py`); без миграционных модулей и слоёв совместимости
- **Безопасность**: смена логики авторизации требует подтверждения владельца; права проверяются на сервере; superadmin не хранится в БД
- **Разделение понятий**: личные настройки UI не требуют прав (identity is the authorization); защиту эндпоинта выбирать по владельцу данных, а не по экрану UI
- **Документация**: README, `docs/technical/`, `docs/guides/` обновляются на русском; PR на русском
- **Тесты**: pytest, без библиотек моков — только простые тестовые двойники
