# Roadmap: Web ANPR System

## Overview

Цикл переводит систему с навигационных прав `tab:*` на ролевую модель: администратор создаёт роли с произвольным названием и матрицей галочек «раздел × Просмотр / Изменение / Удаление» плюс отдельную галочку «Ручное управление реле», назначает роль пользователям, а сервер реально соблюдает эти права на каждом эндпоинте. Путь идёт вертикальными срезами: фундамент (каталог прав, роли в БД, учётки по умолчанию, удаление старой модели), затем управление ролями и пользователями, серверная проверка на всех эндпоинтах, ручное управление реле, немедленное применение прав в открытых потоках, журнал действий и итоговая документация.

## Phases

**Phase Numbering:**
- Integer phases (1, 2, 3): Planned milestone work
- Decimal phases (2.1, 2.2): Urgent insertions (marked with INSERTED)

Decimal phases appear between their surrounding integers in numeric order.

- [ ] **Phase 1: Фундамент модели прав** - Каталог прав, роли с галочками в БД, учётки admin/operator по умолчанию; старая модель `tab:*` удалена
- [ ] **Phase 2: Управление ролями** - Экран и API ролей: создание, переименование, матрица галочек, удаление с защитой назначенных ролей
- [ ] **Phase 3: Управление пользователями** - Экран и API пользователей: ФИО, роль, пароль, блокировка, удаление, время последнего входа
- [ ] **Phase 4: Серверная проверка прав на всех эндпоинтах** - Каждый эндпоинт объявляет право, 403 по Просмотру/Изменению/Удалению, интерфейс скрывает недоступное
- [ ] **Phase 5: Ручное управление реле** - Отдельная галочка для кнопки и хоткея реле; настройка контроллеров — права «Настроек»
- [ ] **Phase 6: Немедленное применение прав и защита потоков** - Смена прав и блокировка действуют без перевхода в API, SSE, MJPEG и интерфейсе; токен не пишется в лог nginx
- [ ] **Phase 7: Журнал действий: входы, экран и хранение** - Запись входов, экран журнала для «Настройки: Просмотр», отдельный срок хранения
- [ ] **Phase 8: Полный журнал действий и документация** - Все изменяющие действия в журнале без секретов и без влияния на само действие; итоговая документация модели прав

## Phase Details

### Phase 1: Фундамент модели прав
**Goal**: Система работает на новой модели: права пользователя задаются его ролью по единому каталогу «раздел × Просмотр/Изменение/Удаление + Ручное управление реле», при развёртывании автоматически создаются роли и учётки по умолчанию, а старая модель `tab:*` удалена целиком
**Mode:** mvp
**Depends on**: Nothing (first phase)
**Requirements**: PERM-01, PERM-08, PERM-09, BOOT-01, BOOT-02, BOOT-03
**Success Criteria** (what must be TRUE):
  1. На чистой БД после запуска можно войти как `admin` и как `operator` с паролями по умолчанию; после смены пароля и перезапуска контейнеров эти учётки не пересоздаются и пароль не сбрасывается
  2. `admin` видит все пять вкладок, `operator` — только «Наблюдение» и «Зоны»; видимость вкладок строится по праву «Просмотр» из матрицы прав текущего пользователя, а список разделов и действий фронтенд получает из единого каталога на сервере
  3. superadmin из `.env` видит все вкладки и единственный видит «Разработку», отсутствует в списке пользователей и может создать пользователя с ролью «Администратор» (в форме пользователя вместо галочек вкладок выбирается одна роль)
  4. В схеме и коде больше нет `users.permissions`, прав `tab:*`, `require_permission("tab:settings")` и проверки `tab:settings` внутри `change_password`; эндпоинты, прежде закрытые `tab:settings`, проверяют права раздела «Настройки» — `operator` получает 403 на чтение настроек
  5. Пользователь без прав на «Настройки» (например, `operator`) меняет собственный пароль, а личные настройки интерфейса работают без каких-либо прав раздела

### Phase 2: Управление ролями
**Goal**: Администратор создаёт, редактирует и удаляет роли с произвольным названием и матрицей галочек прямо в интерфейсе
**Mode:** mvp
**Depends on**: Phase 1
**Requirements**: ROLE-01, ROLE-02, ROLE-03, ROLE-04, ROLE-05, UI-01
**Success Criteria** (what must be TRUE):
  1. На экране ролей администратор создаёт роль с произвольным названием и любым набором галочек в матрице «раздел × Просмотр/Изменение/Удаление» плюс «Ручное управление реле»; роль сразу появляется в списке
  2. Администратор переименовывает роль и меняет её галочки; после перезагрузки страницы сохранённое состояние совпадает с введённым
  3. Список ролей показывает название, отмеченные права и число пользователей с каждой ролью
  4. Удаление роли, назначенной хотя бы одному пользователю, отклоняется понятным сообщением на русском; неназначенная роль удаляется
  5. «Администратор» и «Оператор» переименовываются, редактируются и (если не назначены) удаляются наравне с остальными; переименованная роль даёт ровно свои галочки — название не влияет на права

### Phase 3: Управление пользователями
**Goal**: Администратор ведёт учётные записи в интерфейсе: создаёт пользователей с ФИО и ролью, меняет роль и пароль, блокирует без удаления, удаляет и видит время последнего входа
**Mode:** mvp
**Depends on**: Phase 2
**Requirements**: USER-01, USER-02, USER-03, USER-04, USER-05, USER-06, PERM-07, UI-02
**Success Criteria** (what must be TRUE):
  1. На экране пользователей администратор создаёт пользователя с логином, паролем, ФИО и одной ролью; новый пользователь входит и видит ровно вкладки своей роли
  2. Администратор меняет пользователю ФИО и роль и задаёт ему новый пароль; одна и та же роль назначена нескольким пользователям одновременно
  3. Заблокированный пользователь не может войти, а его уже открытая сессия получает отказ на следующем запросе; после разблокировки вход снова работает; удалённый пользователь исчезает из списка и не может войти
  4. Список пользователей показывает логин, ФИО, роль, статус (активен/заблокирован) и время последнего входа
  5. Пользователь с «Настройки: Просмотр» без «Изменения» видит пользователей и роли, но получает 403 на их создание и изменение; без «Удаления» — 403 на удаление пользователя или роли

### Phase 4: Серверная проверка прав на всех эндпоинтах
**Goal**: Сервер проверяет право раздела на каждом эндпоинте, а интерфейс не предлагает действий, на которые у пользователя нет права, — скрытие вкладок перестаёт быть единственной защитой
**Mode:** mvp
**Depends on**: Phase 3
**Requirements**: PERM-02, PERM-03, PERM-04, PERM-05, UI-03
**Success Criteria** (what must be TRUE):
  1. Тест перебирает все зарегистрированные маршруты приложения и падает, если хоть один эндпоинт не объявил право (раздел + действие) или явный уровень (публичный, «только свой аккаунт», только superadmin)
  2. Пользователь без «Просмотра» раздела не видит его вкладку, а прямые запросы к данным раздела — списки, карточки, медиа событий, снимки и MJPEG-превью каналов, поток событий — получают 403
  3. Пользователь с «Просмотром», но без «Изменения», получает 403 на создание и изменение объектов раздела (зоны, клиента, списка, канала); без «Удаления» — 403 на удаление, в том числе `DELETE /api/channels/{id}`
  4. Кнопки создания, изменения и удаления в интерфейсе скрыты или неактивны, если у пользователя нет соответствующего права

### Phase 5: Ручное управление реле
**Goal**: Пользователь с галочкой «Ручное управление реле» открывает шлагбаум кнопкой или хоткеем, а добавлять, менять и удалять контроллеры могут только пользователи с правами «Настроек»
**Mode:** mvp
**Depends on**: Phase 4
**Requirements**: PERM-06, UI-04
**Success Criteria** (what must be TRUE):
  1. `operator` по умолчанию (у его роли есть галочка «Ручное управление реле») срабатывает реле хоткеем и кнопкой, не имея никаких прав на «Настройки»
  2. У пользователя без галочки кнопки ручного срабатывания нет, хоткей не срабатывает, а прямой вызов API ручного срабатывания возвращает 403
  3. Просмотр, добавление/изменение и удаление контроллеров требуют «Настройки: Просмотр», «Изменение» и «Удаление» соответственно; проверки «только superadmin» на контроллерах больше нет

**UI hint**: yes

### Phase 6: Немедленное применение прав и защита потоков
**Goal**: Изменение прав и блокировка действуют на уже вошедших пользователей без перевхода — в обычных запросах, в открытых потоках SSE и MJPEG и в самом интерфейсе, а токены потоков не утекают в лог nginx
**Mode:** mvp
**Depends on**: Phase 3, Phase 4
**Requirements**: USER-07, UI-06, STRM-01, STRM-02, STRM-03
**Success Criteria** (what must be TRUE):
  1. Администратор снимает у роли галочку или меняет пользователю роль — уже вошедший пользователь получает новый результат проверки (403 или доступ) на следующем же запросе, без перевхода
  2. Интерфейс уже вошедшего пользователя отражает новые права без перевхода: вкладки, кнопки и хоткей реле появляются или исчезают при следующем обновлении данных о текущем пользователе
  3. Открытый поток событий (SSE) закрывается в пределах интервала перепроверки, если пользователя заблокировали или он потерял право «Просмотр», которого требует поток
  4. Открытое MJPEG-превью канала закрывается в пределах интервала перепроверки при блокировке пользователя или потере «Наблюдение: Просмотр»
  5. После открытия потоков событий и превью каналов в access-логе nginx нет токенов доступа из query-string

### Phase 7: Журнал действий: входы, экран и хранение
**Goal**: Администратор видит в интерфейсе журнал действий с входами в систему, а старые записи журнала удаляются по отдельному сроку хранения
**Mode:** mvp
**Depends on**: Phase 3
**Requirements**: AUDIT-02, AUDIT-04, AUDIT-06, UI-05, BOOT-04
**Success Criteria** (what must be TRUE):
  1. Успешные и неудачные входы в систему появляются в журнале действий с временем, логином и результатом
  2. Пользователь с «Настройки: Просмотр» открывает экран журнала действий: новые записи сверху, постраничная навигация; без этого права экрана нет, а API журнала отвечает 403
  3. Входы и действия superadmin в журнал не попадают
  4. Срок хранения журнала задаётся отдельной настройкой, независимой от срока хранения событий, и retention-воркер удаляет записи старше этого срока

### Phase 8: Полный журнал действий и документация
**Goal**: Каждое изменяющее действие пользователя фиксируется в журнале без секретов и без риска сорвать само действие, а документация описывает итоговую модель прав
**Mode:** mvp
**Depends on**: Phase 5, Phase 7
**Requirements**: AUDIT-01, AUDIT-03, AUDIT-05, DOC-01
**Success Criteria** (what must be TRUE):
  1. Создание, изменение, удаление и блокировка пользователей и ролей, изменения каналов, зон, списков, клиентов, контроллеров и настроек, старт/стоп канала, ручное срабатывание реле, экспорт, бэкап, восстановление и ручной запуск retention появляются в журнале: время, логин и ФИО на момент действия, действие, объект, результат
  2. После изменения канала, контроллера и пароля пользователя в записях журнала нет паролей и их хешей, RTSP-адресов с учётными данными и паролей контроллеров
  3. При ошибке записи в журнал ручное открытие шлагбаума и остальные действия всё равно выполняются, а сбой записи фиксируется в логе приложения
  4. README, `docs/technical/` (модель прав, таблица «эндпоинт → право», схема БД) и `docs/guides/` (администратор: роли и пользователи, пароли по умолчанию, восстановление доступа через superadmin) обновлены на русском; раздел авторизации в `AGENTS.md` описывает новую модель вместо «UNDECIDED»

## Решения владельца и открытые вопросы

**Решения владельца после исследования (имеют приоритет над рекомендациями research/):**
- Ручное срабатывание реле — отдельная галочка «Ручное управление реле», не связанная с Просмотром/Изменением/Удалением; добавление, изменение и удаление контроллеров — права «Настроек». Это закрывает исследовательский пункт PROJECT.md о разграничении «настройки» и «использования» контроллеров.
- Управление пользователями и ролями — часть «Настроек»; отдельного права в v1 нет.
- «Настройки» имеют полную тройку Просмотр / Изменение / Удаление, как остальные разделы.
- Роль «Оператор» по умолчанию: Просмотр на «Наблюдение» и «Зоны» + «Ручное управление реле»; роль «Администратор»: все права.
- Защита последнего администратора и от самоблокировки, фильтры и CSV журнала — v2, в этом цикле не планируются. Путь восстановления доступа — superadmin из `.env`.
- Перепроверка открытых потоков SSE/MJPEG и время последнего входа входят в v1.
- Чистая схема без миграции существующих пользователей.

**Открытые вопросы для обсуждения фаз (гипотезы исследования, не решения):**
- **Фаза 1:** как хранить галочку «Ручное управление реле» — отдельный флаг роли или отдельная запись каталога.
- **Фаза 4:** таблицу «эндпоинт → раздел.действие» утверждает владелец до массовой замены проверок. Пограничные случаи: `POST /api/data/retention/run` («Изменение» или «Удаление» «Настроек»); `POST /api/data/backup/database/restore` («Настройки: Изменение» или только superadmin); старт/стоп/рестарт канала («Наблюдение: Изменение»?); экспорт событий («Журнал» или «Настройки»); телеметрия каналов; к какому разделу относится поток событий SSE — у роли «Оператор» по умолчанию нет «Журнала», а живые события показываются в «Наблюдении».
- **Фаза 5:** откуда пользователь без «Настройки: Просмотр» получает привязки реле и хоткеев (сейчас хоткеи строятся из списка контроллеров, закрытого для обычных пользователей) — эндпоинт выбирается по владельцу данных; нужна ли кнопка реле во вкладке «Наблюдение» (сейчас кнопка есть только в настройках контроллера).
- **Фаза 6:** как убрать токен из access-лога — `log_format` nginx без query-string или отдельный короткоживущий токен для потоков.
- **Фаза 7:** запись в журнал сразу проектируется неблокирующей — требование AUDIT-05 проверяется в фазе 8 на ручном срабатывании реле.
