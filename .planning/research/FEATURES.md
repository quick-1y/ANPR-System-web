# Feature Research: права доступа, роли и аудит в VMS / ANPR / парковочных системах

**Domain:** Video Management System (VMS) / ANPR / access control — модель пользователей, ролей и прав
**Researched:** 2026-09-24
**Confidence:** LOW-MEDIUM (все находки получены через `WebSearch`/`WebFetch` по открытой вендорской документации и форумам; официальный API-доступ к Context7/Exa/Ref/Tavily в этой сессии недоступен — `gsd_run query classify-confidence --provider websearch|webfetch` возвращает `LOW` для обоих. Общие паттерны отрасли (разделение «настройка» / «использование», защита от блокировки последнего администратора, аудит-лог) подтверждены **несколькими независимыми источниками** и совпадают с общеотраслевой практикой RBAC, поэтому трактуются как MEDIUM; версия-специфичные детали конкретных вендоров (точные названия чекбоксов) — LOW и должны считаться иллюстрацией, а не спецификацией.)

## Ответ на ключевой открытый вопрос (P: «настройка vs использование» контроллера)

**Наблюдение, подтверждённое во всех проверенных продуктах (Genetec, Hikvision iVMS, Milestone XProtect, частично Axxon/Trassir): «настройка устройства» и «использование устройства» — это везде РАЗНЫЕ права, а не производные одного чекбокса.**

| Продукт | Право «настроить» (добавить/изменить контроллер, реле, камеру) | Право «использовать» (вручную открыть шлагбаум/реле, PTZ, экспорт) | Источник |
|---|---|---|---|
| Genetec Security Center | `Door: Modify` / `Add entity` — административная привилегия | `Door: Unlock` — отдельная операционная привилегия, может быть **переопределена по конкретной двери/зоне** поверх общей роли | techdocs.genetec.com, LOW-MEDIUM |
| Hikvision iVMS-4200 | `Remote Parameters Settings` (конфигурация устройства) | `Remote Alarm Output Control` / `Remote Video Output Control` / `Remote PTZ Control` — отдельные пункты дерева прав | hikvision.com manuals, LOW |
| Milestone XProtect | Добавление/редактирование самого оборудования обычно вообще вне ролевой модели Smart Client — это отдельный административный доступ к Management Server | Роль → вкладка `Output` → право **Activate** на выбранную группу устройств, отдельно от вкладки `PTZ` (Operate) и от `Overall Security` (админ-доступ) | doc.milestonesys.com, LOW |
| Trassir / AutoTrassir | Роль admin — полный доступ к настройке сервера и оборудования | Роль operator — доступ к типовым операционным функциям без прав администрирования сервера | trassir.com, LOW |
| Axxon Next | Роль admin — полная настройка объектов | Отдельные операционные права на объект (управление, вкл. релейные/тревожные выходы) — детали не подтверждены документацией, но общая архитектура (роль → права по разделам оборудования) аналогична | doc.axxonsoft.com, LOW (не удалось получить точный список чекбоксов) |
| Парковочные ANPR-платформы (Parklio, PARQ, Unity5 и т.п.) | Настройка правил доступа/бизнес-логики — Administrator | Ручное открытие шлагбара оператором — типично доступно и Operator, как отдельная кнопка на экране мониторинга, не требующая прав конфигурации | общие маркетинговые/справочные материалы, LOW |

**Вывод:** ни один изученный продукт не связывает «ручную активацию реле/шлагбаума» с правом «настроить устройство». Везде это разные оси: конфигурация оборудования = административная привилегия; ручное срабатывание = операционная привилегия, обычно доступная той же роли, что имеет право на живой просмотр/работу с этим разделом (Observation/Live), а не разделу настроек.

### Рекомендация для этого проекта (гипотеза, не решение)

Текущая модель цикла фиксирует 5 разделов (Наблюдение, Журнал, Зоны, Клиенты, Настройки) с галочками Просмотр/Изменение/Удаление, без разбивки «Настроек» и без прав по объектам в этом цикле. Контроллеры сегодня физически конфигурируются через панель, тяготеющую к «Настройкам».

**Гипотеза A (рекомендуемая).** Ручная активация реле/шлагбаума — операционное действие раздела **Наблюдение**, разрешённое правом **Изменение** на Наблюдение. Настройка самого контроллера (адрес, пароль, тип, время реле, привязка к каналу) остаётся в **Настройках** (Изменение/Удаление). Это прямое повторение паттерна Genetec/Hikvision/Milestone выше и совпадает с дефолтной ролью «Оператор» из PROJECT.md (Наблюдение + Зоны, без Настроек) — иначе оператор по умолчанию не сможет открыть шлагбаум вручную, что противоречит его роли на объекте (охранник на КПП).
- Плюсы: не требует нового права/раздела сверх уже принятой модели; согласуется с default-ролями владельца.
- Минусы: раздел «Наблюдение» приобретает не только просмотровую, но и управляющую семантику; право «Удаление» для Наблюдения остаётся семантически пустым (нет сущности для удаления) — требует явного решения (не показывать галочку Удаление для Наблюдения, либо оставить как «зарезервировано»).

**Гипотеза B (альтернатива, ближе к энтерпрайз-паттерну, но больше объёма работы).** Завести отдельное булево право «Ручное управление реле», не привязанное к CRUD-глаголам View/Edit/Delete — так это моделируют Genetec и Hikvision (право-действие, а не производная от Edit). Технически честнее, но расширяет матрицу прав сверх зафиксированного в этом цикле формата (5 разделов × 3 галочки) и требует изменения UI роли раньше запланированного «дробления Настроек». Стоит рассмотреть в фазе, где будет решаться дробление «Настроек» на подразделы (уже вынесено в Out of Scope этого цикла).

**Гипотеза C (не рекомендуется).** Держать ручную активацию под Настройки-Изменение (нынешняя фактическая близость controllers к settings-подобной панели). Отклоняется: тогда оператор без Настроек не сможет открыть шлагбаум ни при каких обстоятельствах, что противоречит реальному сценарию использования (пропустить машину вручную) и противоречит всем изученным аналогам.

Рекомендация: принять гипотезу A на этот цикл, зафиксировать переход к гипотезе B как известный технический долг для фазы дробления «Настроек».

## Feature Landscape

### Table Stakes (Users Expect These)

Функции, которые уже приняты как Active-требования владельца и одновременно подтверждаются как отраслевая норма — без них продукт будет восприниматься как незаконченный или небезопасный по сравнению с любым конкурентом (включая бюджетные Trassir/Macroscop).

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Произвольные роли + чек-боксы Просмотр/Изменение/Удаление по разделам | Все проверенные VMS (Genetec, Milestone, Hikvision, Trassir, Axxon) дают кастомные роли с деревом прав | MEDIUM | Уже в Active-скоупе цикла |
| Разделение права «настроить устройство» и «использовать устройство» (см. выше) | Универсальный паттерн отрасли, без него оператор либо не может работать, либо имеет лишний доступ к конфигурации | MEDIUM | Требует явного архитектурного решения (см. гипотезу A/B выше) |
| Серверная проверка прав на КАЖДОМ эндпоинте, а не только скрытие вкладки | Текущий аудит (P18/P19) показывает именно этот дефект как критичный; во всех проверенных продуктах права проверяет сервер, а не только клиент | HIGH | Уже Active-требование; закрывает 46 незащищённых эндпоинтов |
| Блокировка пользователя без удаления (is_active) | Есть во всех проверенных продуктах (enable/disable account) | LOW | Уже Active-требование; колонка `is_active` в `users` уже существует |
| Немедленное применение изменения роли/прав к уже вошедшим пользователям | Стандартная практика — доступ пересчитывается на сервере при каждом запросе, а не кэшируется в токене на весь срок его жизни | HIGH | **Архитектурная зависимость**: права нельзя «печь» в тело JWT надолго — при каждом запросе нужен свежий lookup роли/прав из БД (или очень короткий TTL + пересчёт), иначе отзыв доступа не будет мгновенным при stateless JWT без хранилища сессий (проект намеренно без Redis) |
| Журнал действий пользователей (кто/когда/что) | Есть во всех проверенных продуктах в том или ином виде (Genetec audit trail, Milestone system log, Hikvision operation log, Orchid audit log) | MEDIUM-HIGH | См. отдельный раздел ниже |
| Защита от блокировки системы: нельзя удалить/заблокировать/разжаловать последнего пользователя с правами администратора | Повсеместный паттерн современных RBAC-систем (Zitadel, Azure AD Global Admin, множество open-source примеров) — критично для проекта с одним админом на объекте | MEDIUM | Нужно точное определение «администратора» в свободной ролевой модели — см. Feature Dependencies |
| Пользователь не может сам себя заблокировать / снять с себя последнее администраторское право | То же соображение — self-lockout — частый источник инцидентов в свободных ролевых моделях | LOW-MEDIUM | Проще всего реализовать как частный случай защиты «последнего администратора» |

| Экспорт журнала действий в CSV, с фильтрами по пользователю/дате/типу действия | Прямая аналогия с уже существующим экспортом событий ANPR в этом проекте (`app/shared/data_lifecycle.py`) | MEDIUM | Переиспользовать существующий паттерн экспорта, не изобретать новый |

| Несколько ролей на одного пользователя / композиция ролей | Гибкость, как в некоторых enterprise-системах с группами | Неочевидные правила приоритета при конфликте прав (union vs intersection, allow-overrides-deny или наоборот), взрыв числа комбинаций для тестирования, лишний UI. | Полная политика паролей (сложность, история, принудительная ротация) | Стандарт безопасности в enterprise VMS с интеграцией AD/LDAP | Для закрытой on-prem инсталляции с несколькими локальными пользователями это трение без выигрыша; владелец явно отказался от принуждения к смене пароля по умолчанию | Держать текущую минимальную длину, но явно задокументировать рекомендацию сменить дефолтные пароли; технически не принуждать |

| Условные/расписанные права (доступ только в рабочие часы, временные роли) | Встречается в продвинутых access control платформах | Существенно увеличивает модель данных и UI ради функции, не запрошенной владельцем и не входящей ни в один Active-пункт | Не строить; переоценить, если появится конкретный кейс |

## Feature Dependencies

```
Роль (произвольное имя + права по разделам)
    └──requires──> Сущность «Право по разделу» (Просмотр/Изменение/Удаление × 5 разделов)

Серверная проверка прав на каждом эндпоинте (закрытие P19)
    └──requires──> Единый механизм разрешения "роль пользователя → эффективные права" на бэкенде
                       └──requires──> Роль (см. выше)

Немедленное применение изменения прав уже вошедшим пользователям
    └──requires──> Права читаются из БД при каждом запросе (не «запекаются» в JWT надолго)
                       └──conflicts (частично)──> Полное stateless-кэширование прав в JWT на весь TTL

Ручная активация реле/шлагбаута из «Наблюдения» (гипотеза A)
    └──requires──> Решение: право живёт в разделе Наблюдение, а не Настройки
    └──enhances──> Существующую интеграцию с контроллерами (`controllers/service.py`)

Журнал действий пользователей
    └──requires──> Единая точка записи аудит-события (декоратор/хелпер), подключаемая к каждому мутирующему эндпоинту
    └──enhances──> (сильно) работу цикла P18/P19-рефакторинга — оба меняют одни и те же 46+ обработчиков,
                    имеет смысл делать аудит-логирование в той же фазе/сразу вслед за enforcement,
                    а не отдельным проходом по тем же файлам

Защита от блокировки последнего администратора
    └──requires──> Определение «администратор» в свободной ролевой модели
                       (рекомендация: пользователь, чья роль имеет право «Изменение» на раздел «Настройки»)
    └──requires──> Подсчёт активных пользователей с этим правом в реальном времени при попытке блокировки/удаления/смены роли

Отображение последнего входа
    └──requires──> Колонка `users.last_login_at`, запись при успешной аутентификации (независимая, без блокеров)
```

### Dependency Notes

- **Немедленное применение прав requires серверный lookup «на лету».** Это самая важная архитектурная зависимость всего цикла: если права будут вшиты в payload JWT (как это отчасти происходит сейчас — `permissions` читаются из токена/БД по-разному в разных хендлерах), «мгновенное» изменение прав невозможно без дополнительного хранилища отзыва токенов, которое проект намеренно не заводит (без Redis). Прямое решение — не кэшировать права в токене длительно: на каждый защищённый запрос заново резолвить роль → права из БД (дешёвый JOIN/lookup), и заодно проверять `is_active`. Это же решение бесплатно даёт «блокировка пользователя действует немедленно, без re-login».
- **Журнал действий should быть частью той же фазы, что и enforcement-рефакторинг (P19).** Технически дешевле добавить вызов аудит-хелпера в тот же момент, когда переписывается защита каждого из 46+ эндпоинтов, чем проходить по тем же файлам дважды.
- **Защита последнего администратора requires чёткое определение «администратор» в свободной ролевой модели.** Раз ролей с произвольными именами может быть много, нужен операционный критерий, а не имя роли «Администратор». Рекомендация: администратором для целей этой защиты считается любой активный пользователь, чья роль имеет право **Изменение на раздел «Настройки»** (ближайший в этой модели аналог «полного контроля над системой» — без него нельзя управлять пользователями/ролями). Это же правило переиспользуется для self-lockout защиты.
- **Ручная активация реле enhances, а не requires существующую интеграцию контроллеров** — `controllers/service.py` уже реализует HTTP-адаптеры; вопрос только в том, каким правом закрыт вызов, а не в новой интеграции.

## MVP Definition

### Launch With (этот цикл, соответствует Active-требованиям PROJECT.md)

- [ ] Роль: произвольное имя + права Просмотр/Изменение/Удаление по 5 разделам (Настройки — одна галочка) — уже Active
- [ ] Серверная проверка прав на всех эндпоинтах, вкладка видна по праву «Просмотр» — уже Active, закрывает P18/P19
- [ ] Пользователь: логин/пароль/ФИО/одна роль, блокировка без удаления — уже Active
- [ ] Немедленное применение изменений роли/прав без пере-входа (требует lookup «на лету», см. Dependency Notes) — уже Active
- [ ] Журнал действий пользователей (кто/когда/что), с фильтрами и CSV-экспортом — уже Active, детали фильтров/полей ниже
- [ ] Дефолтные роли/пользователи `admin`/`operator`, обычные и редактируемые — уже Active
- [ ] superadmin → «Разработка», без строки в `users` — уже Active
- [ ] **Решение по контроллерам: принять гипотезу A** (ручная активация реле = право Изменение на «Наблюдение», настройка контроллера = «Настройки») — закрывает открытый пункт Active-списка
- [ ] Защита от блокировки последнего администратора (по критерию «Изменение на Настройки») + запрет самоблокировки — новое, но table stakes, дёшево реализуется вместе с User CRUD
- [ ] Отображение времени последнего входа в списке пользователей — новое, LOW complexity, добавить в этот же цикл

### Add After Validation (v1.x)

- [ ] Дробление «Настроек» на подразделы с отдельными правами (уже отложено владельцем; естественно тянет за собой переход от гипотезы A к гипотезе B для контроллеров)
- [ ] Права по конкретным каналам/контроллерам (per-object scoping) — уже отложено владельцем
- [ ] Более богатый UI журнала действий (группировка по сессиям, визуальные индикаторы аномалий)
- [ ] Отдельная (от ANPR-событий) настраиваемая политика хранения аудит-лога, если объём/требования потребуют

### Future Consideration (v2+)

- [ ] LDAP/AD/SSO-интеграция — только при появлении корпоративного клиента с существующим каталогом
- [ ] Несколько ролей на пользователя / композиция ролей
- [ ] Полноценное мгновенное принудительное завершение сессии (потребует token-revocation хранилища, сейчас вне стека)
- [ ] Условные/расписанные права

## Что ожидается от журнала действий (детализация вопроса 3)

На основе паттернов проверенных продуктов (Genetec audit trail, Milestone system/audit log, Hikvision operation log, Orchid Core VMS audit log — LOW-MEDIUM confidence, но взаимно согласующиеся):

- **Какие действия логировать (минимум для этого продукта):** вход/выход (успех и неудача), создание/изменение/удаление/блокировка пользователя, создание/изменение/удаление роли, изменение прав роли, создание/изменение/удаление/старт/стоп канала, ручная активация реле/шлагбаума (важно — именно то действие, вокруг которого ключевой вопрос этого исследования), создание/изменение/удаление зоны, списка, клиента, изменение настроек инстанса, запуск экспорта/бэкапа/восстановления, запуск retention вручную.
- **Чего НЕ логировать:** обычные GET-запросы/чтения, живой просмотр видео как таковой (иначе лог тонет в шуме) — логировать только состояние-изменяющие действия и вход/выход, по аналогии с Orchid Core, который отдельно фиксирует именно значимые операции (PTZ-перемещение, экспорт, сессии), а не каждый кадр или запрос.
- **Поля записи:** время (UTC на сервере, отображение — в зоне интерфейса, см. уже принятое решение O-4 из `configuration-architecture.md`), пользователь (логин + ФИО на момент события — хранить снимок ФИО, а не только ссылку, чтобы запись оставалась читаемой после удаления пользователя), тип действия, целевой объект (например, «канал: Въезд, id=12»), результат (успех/отказ, включая отказ по правам), при изменении — старое/новое значение хотя бы для ролей и прав.
- **Фильтры:** по пользователю, по типу действия/разделу, по диапазону дат — минимальный набор, совпадающий с фильтрами, которые уже есть в существующем Журнале событий ANPR (`app/web/js/journal.js`) — переиспользовать тот же UI-паттерн.
- **Экспорт:** CSV, тем же механизмом, что уже используется для экспорта данных (`app/shared/data_lifecycle.py`) — не изобретать второй экспортный пайплайн.
- **Хранение/retention:** конкретный срок — решение владельца, не диктуется исследованием; технически стоит сделать retention аудит-лога независимо конфигурируемым от retention событий ANPR (разные регуляторные ожидания: ANPR-события — оперативные данные, аудит действий пользователей — скорее долгосрочный контроль/расследование инцидентов), но это MEDIUM-приоритетная деталь, не блокер MVP.
