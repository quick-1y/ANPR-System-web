# Исследование: типичные ошибки (Pitfalls)

**Домен:** RBAC (произвольные роли + галочки Просмотр/Изменение/Удаление), блокировка пользователей, немедленное применение прав к активным JWT-сессиям, журнал действий — для self-hosted FastAPI + PostgreSQL системы управления физическими шлагбаумами/воротами (ANPR) с видео по MJPEG и событиями по SSE.
**Исследовано:** 2026-09-24
**Уверенность:** HIGH (находки по кодовой базе — прочитан код напрямую) / MEDIUM (общие практики RBAC/JWT/аудита — веб-поиск)

> Все находки в разделе «Критические ошибки» проверены чтением реального кода на коммите `ebbc070` (`app/api/deps.py`, `app/api/routers/auth.py`, `app/api/routers/users.py`, `app/api/routers/events.py`, `app/api/routers/channels.py`, `app/api/routers/controllers.py`, `tests/test_permission_guards.py`, `nginx/default.conf`, `database/postgres/schema.sql`). Это не гипотетические риски RBAC-систем вообще — это конкретные места в этом репозитории, где новая модель прав либо унаследует, либо обязана закрыть проблему.

## Критические ошибки

### Ошибка 1: Открытые API под видимостью вкладок (frontend-only enforcement)

**В чём проявляется:**
Права проверяются в UI (скрытие вкладки/кнопки), но соответствующий REST-эндпоинт доступен любому аутентифицированному пользователю или вообще без проверки конкретного права.

**Почему это уже факт, а не риск:**
Аудит (`docs/roadmap/configuration-architecture.md`, 2.7, P18/P19) и `.planning/codebase/CONCERNS.md` зафиксировали: `tab:obs`, `tab:journal`, `tab:clients`, `tab:zones` не проверяются на сервере вообще; 46 эндпоинтов защищены только фактом входа (`get_current_user`), включая `DELETE /api/channels/{id}`, `DELETE /api/zones/{id}`, `DELETE /api/lists/{id}`. Подтверждено чтением `app/api/routers/channels.py`, `zones.py` — там нет `require_permission`/`require_access`, только `Depends(get_current_user)`.

**Как избежать:**
Переход на новую модель прав должен быть полным по определению, а не точечным патчем: каждый маршрут в `app/api/routers/` явно декларирует уровень доступа через адаптер (`app/api/deps.py`), а не наследует «просто вход выполнен». Раздел «Просмотр» — это видимость вкладки И право читать данные раздела через API одновременно (одно и то же условие, а не два независимых).

**Признаки проблемы:**
Любой роутер, где `Depends(get_current_user)` — единственная проверка перед операцией записи/удаления. Grep по `app/api/routers/*.py` на `Depends(get_current_user)` без соседнего `require_permission`/`require_access` рядом с `@router.delete`/`@router.put`/`@router.post`.

**Фаза:** backend-применение прав (перевод существующих роутеров с `get_current_user` на новую модель) — ядро этого цикла.

### Ошибка 2: Забытые эндпоинты при миграции модели прав

**В чём проявляется:**
Часть маршрутов переводится на новую модель, часть — по забывчивости — остаётся на старой (`get_current_user` без проверки права) или получает право «на глазок», без единого прохода по списку всех маршрутов.

**Почему это уже факт:**
Текущий тест `tests/test_permission_guards.py` не решает эту задачу — он проверяет 5 конкретных роутеров (`settings`, `controllers`, `debug`, `data`, часть `auth`) на присутствие строки `require_role`/`require_permission` в исходнике грепом по файлу. Он не перечисляет реальные маршруты FastAPI и не покрывает `channels.py`, `zones.py`, `lists.py`, `clients.py`, `events.py`, `journal.py` — то есть именно те роутеры, где сегодня дыры.

**Как избежать:**
Тест-инвариант, который итерирует `app.routes` (а не читает файл как текст) и для каждого маршрута из белого списка «должен быть защищён» (всё, что не `public`) проверяет наличие зависимости, резолвящейся в `require_access(...)`/`require_permission(...)`. Список маршрутов, помеченных `public`/`authenticated`, — явный и подлежит код-ревью при каждом PR, а не подразумевается по умолчанию. Это превращает «не забыли ли эндпоинт» из ручной проверки в CI-гейт.

**Признаки проблемы:**
Тест проходит, потому что покрывает только те роутеры, что были защищены на момент его написания — новый роутер/эндпоинт не ломает тест, значит тест ничего не гарантирует для будущего кода.

**Фаза:** backend-применение прав, с обязательным добавлением/переписыванием `test_permission_guards.py` в рамках той же фазы, не отдельным тикетом «потом».

### Ошибка 3: SSE/MJPEG/медиа обходят проверку — токен в query-string, поток не перепроверяется после отзыва

**В чём проявляется:**
Два независимых риска, оба подтверждены в этом репозитории:

1. **Токен в URL.** `_extract_token()` (`app/api/deps.py:122`) намеренно принимает `?token=<jwt>` — это необходимо, так как `<img>`/`EventSource` не могут выставить заголовок `Authorization`. Но `nginx/default.conf` не переопределяет `log_format`, значит используется дефолтный `combined`, включающий `$request` — то есть **токен из query-string пишется в access-лог nginx в открытом виде**. Тот же токен утекает в `Referer` при переходах со страницы предпросмотра, в историю браузера, в прокси-логи между клиентом и сервером.
2. **Долгоживущий поток не перепроверяется.** `stream_events()` (`app/api/routers/events.py:103`) и `channel_preview_stream()` (`app/api/routers/channels.py:79`) проверяют пользователя **один раз** — в момент открытия соединения через `Depends(get_current_user)`. Дальше генератор крутится в цикле (`while not container.stream_shutdown.is_set()`) без повторного обращения к БД. `nginx/default.conf` явно ставит `proxy_read_timeout 1h` для `/api/events/stream` — то есть окно, в течение которого заблокированный/лишённый прав пользователь продолжает получать события или видео, может достигать часа, пока не истечёт JWT или клиент не переподключится.

**Почему это возникает:**
SSE/MJPEG — это НЕ request/response, а долгоживущее соединение; стандартный паттерн FastAPI-зависимостей (`Depends`) резолвится один раз при входе в обработчик, а не на каждой итерации генератора. Разработчики переносят привычку «Depends = защищено» на потоковые эндпоинты, не замечая, что защита действует только на handshake.

**Как избежать:**
- В генераторе `stream_events`/`channel_preview_stream` добавить периодическую (например, раз в 15–30 с, синхронно с уже существующим ping/keep-alive) повторную проверку: пользователь всё ещё существует, `is_active=True`, и (для канальных потоков) сохраняет право `Просмотр` на нужный раздел — если нет, закрыть поток.
- Не полагаться только на укорачивание TTL JWT для потоков — при `proxy_read_timeout 1h` токен, выданный с TTL 30 минут, всё равно может пережить остаток соединения, если поток был открыт до истечения и завершится позже по вине nginx-таймаута, а не по вине expiry.
- Не логировать query-string токенов: либо развести `log_format` в nginx так, чтобы не писать `$request` целиком для `/api/*` со query, либо (предпочтительно) перейти на короткоживущий одноразовый stream-токен, отдельный от основного JWT, для media/SSE/MJPEG эндпоинтов — так утечка в лог не даёт доступа к остальному API.

**Признаки проблемы:**
`docker compose logs nginx | grep token=` находит токены; заблокированный во время активного SSE-соединения пользователь продолжает получать `data:` события ещё N минут после блокировки.

**Фаза:** применение прав к SSE/MJPEG — отдельная задача внутри фазы backend-применения прав; не входит «бесплатно» в общий переход на `require_access`, так как обычные HTTP-эндпоинты этой проблемы не имеют (см. Ошибку 4).

### Ошибка 4: «Протухшие» claims в JWT после смены роли/блокировки (в этой кодовой базе — уже решено правильно, не сломать при редизайне)

**В чём проявляется в индустрии:**
Классическая ошибка RBAC-систем — класть роль/права прямо в JWT-payload и доверять им до истечения токена; после блокировки или смены роли пользователь продолжает действовать со старыми правами до re-login.

**Что реально в этой кодовой базе (важная находка):**
Эта ошибка **уже не совершена**. `create_access_token()` (`app/api/auth_utils.py:30`) кладёт в payload только `sub` (user_id) и `role` — но `role` из токена нигде не используется для авторизации: `get_current_user()` (`app/api/deps.py:21`) каждый раз заново читает пользователя из БД (`container.user_db.find_by_id(user_id)`), включая `is_active` и (для реальных пользователей) `permissions`. `require_role`/`require_permission` проверяют именно этот свежепрочитанный объект, а не поле из токена. Значит: блокировка (`is_active=False`) и смена прав уже сегодня применяются **на следующий же HTTP-запрос**, без re-login — то есть именно то поведение, которое требует `PROJECT.md` («Изменение роли/прав применяется к уже вошедшим пользователям сразу, без перевхода»).

**Реальный риск для этого цикла — не «протухание», а регресс:**
При переходе на произвольные роли + галочки велик соблазн, ради производительности (не ходить в БД на каждый запрос), закешировать вычисленный набор прав — либо в самом JWT (вернуться к «роль в токене»), либо в in-memory кеше без инвалидации при `PUT /api/roles/{id}` или блокировке пользователя. Это откатит уже работающее свойство системы.

**Как избежать:**
Явно зафиксировать как архитектурное ограничение: источник истины для прав — БД, читается на каждый запрос (как сейчас), а не JWT-claim и не TTL-кеш без инвалидации. Если появится реальная потребность в кеше (профилирование покажет нагрузку на `users`/`roles` таблицы) — кеш обязан инвалидироваться синхронно при `PUT`/`DELETE` роли и при блокировке пользователя, а не по времени.
Отдельно закрыть исключение из Ошибки 3 (SSE/MJPEG) — там как раз кеш есть по факту (соединение открыто с правами на момент подключения).

**Признаки проблемы:**
В PR встречается `permissions` или список прав, сериализованный в JWT-payload, или новый module-level `dict`/`lru_cache`, хранящий права пользователя без явного `invalidate()`, вызываемого из обработчиков смены роли/блокировки.

**Фаза:** проектирование схемы ролей/прав — зафиксировать это ограничение в самом начале (как ADR/примечание в коде), до того как кто-то напишет кеш «для производительности».

### Ошибка 5: Блокировки (lockout) — самоблокировка, удаление последней управляющей роли, удаление роли «в использовании»

**В чём проявляется:**
Три отдельных сценария, ведущих к тому, что никто не может управлять пользователями/ролями:

1. **Администратор лишает прав сам себя.** Сегодня `update_user()` (`app/api/routers/users.py:82`) защищает только явную деактивацию себя же (`user_id == current_user["id"] and body.is_active is False` → 400). Но **смену собственной роли/прав она не защищает вообще** — админ может назначить себе роль без `tab:settings`/будущего эквивалента и потерять доступ к управлению пользователями без какого-либо предупреждения.
2. **Удаление роли, всё ещё назначенной пользователям.** Проектируемая модель (`PROJECT.md`: «Роль: произвольное название... роли создаются, редактируются и удаляются через UI») предполагает удаляемые роли. Если `users.role` — просто текст/FK без защиты, удаление роли, на которую ссылаются активные пользователи, либо ломает FK (если она есть), либо молча оставляет пользователей с «висячей» ролью без прав (если FK нет) — оба исхода плохие: первый — 500 из БД, второй — тихий lockout этих пользователей.
3. **Удаление/обезличивание единственной роли с правом управления пользователями/ролями.** Поскольку роли произвольные и без «зашитой логики» (явное решение владельца в `PROJECT.md`), ничто не мешает администратору удалить или обеднить единственную роль, дающую доступ к разделу «Настройки» (где по решению этого цикла живёт управление пользователями) — и тогда ни один пользователь в системе, включая всех admin-подобных, больше не может зайти в управление ролями. Единственный путь назад — technical superadmin через `.env`, который по дизайну «нигде не отображается» и должен оставаться крайним случаем, а не штатным способом восстановления.

**Как избежать:**
- Расширить существующий self-guard: запретить не только `is_active=False`, но и любое изменение **своей же** роли/прав, если результат лишает исполнителя права управления пользователями/ролями (симметрично текущей защите от самодеактивации — тот же паттерн, тот же файл).
- Перед удалением роли — проверка `SELECT count(*) FROM users WHERE role_id = ?`; при наличии назначений — 409 с понятным сообщением («роль назначена N пользователям»), а не тихое каскадное поведение.
- Инвариант на уровне приложения (не обязательно БД-констрейнт, но обязательно проверяемый в тесте и в хендлере): в системе всегда должна остаться хотя бы одна роль с правом управления пользователями/ролями, назначенная хотя бы одному активному пользователю, либо polagаться на superadmin как явно задокументированный последний рубеж (тогда это нужно прямо написать в `docs/guides/` — «если некому назначать роли, войдите как superadmin»).

**Признаки проблемы:**
После правки роли/удаления роли ни один обычный пользователь (кроме superadmin) не видит раздел управления пользователями; тест на этот сценарий отсутствует (сегодня в `tests/` таких тестов нет вообще — `test_permission_guards.py` не покрывает self-lock по роли).

**Фаза:** проектирование сущности «Роль» (CRUD-эндпоинты ролей) + backend-применение прав — оба сценария (удаление роли, самоограничение) должны быть закрыты до того, как UI для управления ролями станет доступен реальным администраторам.

### Ошибка 6: Эскалация привилегий через самого себя — редактирование собственной роли и выдача прав, которых не имеешь сам

**В чём проявляется:**
Пользователь с правом «Изменение» раздела «Настройки» (куда, по решению этого цикла, попадает управление ролями/пользователями — «Настройки» одной галочкой в этом цикле, дробление отложено) может:
- отредактировать **свою собственную** роль, выдав себе любые дополнительные галочки (включая те, которых у него не было);
- отредактировать **чужую** роль или создать новую, выдав ей права, которых сам редактор не имеет (например, оператор с изолированным правом на управление ролями — если такое когда-то будет назначено — сможет создать себе роль с полным доступом к «Наблюдению», «Журналу» и т. д., даже не имея их сам).

**Почему это реальный риск именно здесь:**
Явное решение владельца — «Настройки» в этом цикле не дробятся на подразделы (`PROJECT.md`, Out of Scope). Значит любой, кто имеет «Настройки: Изменение», по факту получает root-доступ к системе прав целиком, а не только к своей узкой зоне ответственности. Это осознанный компромисс владельца, но он должен быть явно задокументирован как принятый риск, а не всплыть неожиданно при аудите.

**Как избежать (без нарушения решения «не дробить Настройки в этом цикле»):**
- Минимальный барьер, не требующий дробления прав: **запретить пользователю редактировать роль, которая назначена ему самому** (аналог существующего self-deactivation guard) — тогда эскалация «выдай себе больше» требует хотя бы создания второй роли и переключения на неё через другого администратора, что уже не тихая самостоятельная эскалация.
- Задокументировать явно (в `docs/guides/` для администратора и в PR этого цикла): «право Настройки:Изменение равносильно полному контролю над правами доступа в системе — назначайте его так же осторожно, как раньше — роль администратора». Это не обходит риск, а делает его сознательным, что соответствует политике проекта («proposals are hypotheses», но принятые решения владельца — не повод оставлять риск незадокументированным).
- Не решать эскалацию через «можно выдать только то, что имеешь сам» в этом цикле — с одной галочкой на весь раздел «Настройки» это правило ничего не ограничивает (у имеющего Настройки:Изменение и так есть право редактировать сами роли, значит по этому правилу он может выдать себе любые права раздела «Настройки» — раздела, где это и происходит). Помечать эту идею как задел для фазы дробления «Настроек».

**Признаки проблемы:**
Оператор с узкой ролью, получивший доступ к разделу редактирования ролей по ошибке конфигурации, спустя один клик становится администратором без следа в журнале действий, если аудит-лог (Ошибка 8) не пишет «кто изменил роль X на Y».

**Фаза:** проектирование сущности «Роль» — минимум self-edit guard; полная модель ограничения «выдавай не больше своего» — явно отложена и должна попасть в backlog для фазы дробления «Настроек», не в этот цикл.

### Ошибка 7: Дефолтные пользователи `admin`/`operator` с известными паролями без принуждения к смене

**В чём проявляется:**
`PROJECT.md` фиксирует осознанное решение владельца: при разворачивании в БД создаются `admin` и `operator` с паролями по умолчанию, смена не принуждается. Система управляет физическими шлагбаумами/воротами — компрометация дефолтного пароля означает не утечку данных, а физический доступ.

**Мера, которая уже существует в коде и которую нужно просто расширить, а не изобретать:**
Для technical superadmin уже реализован ровно нужный паттерн: `superadmin_password_is_default()` (`config/env_settings.py`) + `warn_default_password` в `LoginResponse` (`app/api/routers/auth.py:116`) — фронтенд получает флаг и может показать предупреждение. Для обычных пользователей уже есть колонка `password_changed_at` в схеме (`database/postgres/schema.sql:128`) и `change_password` уже вызывает `update_password`, но — проверено чтением `auth.py:167` — `warn_default_password` для обычных пользователей сегодня выставляется только для `role == "superadmin"`; для сидируемых `admin`/`operator` этот же расчёт (`password_changed_at is None` → предупреждение) не подключён нигде.

**Как избежать, уважая решение владельца не принуждать смену:**
- Распространить уже существующий `warn_default_password`-паттерн на **любого** пользователя с `password_changed_at IS NULL`, не только на superadmin — один и тот же флаг в `LoginResponse`, один код.
- Не разовое уведомление при логине, а постоянный баннер в UI, пока пароль не сменён (одноразовый тост легко закрыть и забыть — для гейта на физический доступ этого недостаточно).
- Событие «вход под паролем по умолчанию» — обязательная запись в новый журнал действий (Ошибка 8) отдельным типом события с уровнем не ниже предупреждения, чтобы это было видно в аудите, а не только в мимолётном UI-баннере.
- В `docs/guides/` для интегратора/администратора — явная инструкция сменить пароли `admin`/`operator` сразу после разворачивания, с указанием, что это физический риск (управление шлагбаумом), а не просто гигиена.
- Не предлагать заново «принудительную смену» или «случайный пароль на первом старте» как требование — это прямо закрыто в Out of Scope `PROJECT.md`; но стоит зафиксировать как открытый риск в документации на случай пересмотра решения владельцем позже.

**Признаки проблемы:**
`grep password_changed_at` показывает, что колонка читается только для `role == "superadmin"`; в проде спустя месяцы `admin`/`operator` всё ещё на дефолтных паролях и это никак не видно администратору, кроме как SQL-запросом вручную.

**Фаза:** seed-пользователи + журнал действий — оба должны landить вместе, иначе предупреждение о дефолтном пароле некуда писать в аудит.

### Ошибка 8: Дыры в журнале действий — не логируются неудачные входы, логируются секреты, неограниченный рост, запись аудита ломает основное действие

**В чём проявляется — четыре независимых проблемы:**

1. **Неудачные входы и отказы в доступе (403) сегодня идут только в текстовый лог, не в будущий структурированный аудит.** `auth.py` уже логирует `login_failed` (`logger.warning`, строки 102/136/144/153) — но это `common/logging` → ротируемый почасовой файл (`HourlyFileHandler`), а не таблица, доступная через UI журнала действий. Если требование `PROJECT.md` («журнал действий пользователей: кто/когда... открыл шлагбаум, изменил роль») трактовать узко — только успешные действия аутентифицированных пользователей — неудачные попытки входа и попытки вызвать эндпоинт без права (403) останутся видны только через `docker compose logs`, а не администратору системы через UI. Для системы контроля доступа это как раз тот сигнал, который нужнее всего (кто-то подбирает пароль к `admin`).
2. **Логирование секретов в самом аудите.** Существующее правило проекта («не логировать `channels.source` целиком, не логировать `controllers.password»`, `.planning/codebase/CONCERNS.md` → «Credential Exposure in Logs») относится к текстовым логам. Новый журнал действий — **дополнительная, более широко просматриваемая поверхность** (вероятно, доступна через UI любому с правом «Настройки: Просмотр» или отдельным правом на журнал, то есть шире, чем «кто читает контейнерные логи через SSH»). Наивная реализация «сохраним весь payload запроса как JSON в audit_log» для действия «изменил канал» или «изменил контроллер» запишет RTSP-креды и пароль контроллера в открытом виде в таблицу, которую видит группа администраторов, а не только суперадмин. Нужна redaction на границе записи аудита, симметричная той, что уже действует для API-ответов (`channels.source`/`controllers.password` не возвращаются полностью — то же должно быть верно для audit-записи).
3. **Неограниченный рост.** В проекте уже есть работающий паттерн ретеншна для `events` (`app/shared/data_lifecycle.py`, retention worker, `RetentionPolicy`). Журнал действий — та же по форме проблема (растущая таблица с меткой времени), и должен переиспользовать существующий retention-механизм, а не быть новой безлимитной таблицей без пути очистки. Отдельный вопрос: нужна ли на audit_log отдельная (возможно, более долгая) политика хранения, чем на `events` — но механизм переиспользуется, не изобретается заново.
4. **Синхронная запись аудита ломает основное действие.** Это особенно опасно для действия «открыть шлагбаром/ворота» через `controller_service.send_command()` (`app/api/routers/controllers.py:62`). Пул соединений PostgreSQL уже узкое место (`min=2, max=10`, зафиксировано в `CONCERNS.md` как «Connection Pool Size» лимит). Если запись в `audit_log` делается синхронно, в той же request-транзакции, что и физическая команда на реле, и пул исчерпан/БД временно недоступна — нельзя допустить, чтобы отказ записи аудита заблокировал реальное открытие ворот (охранник должен проехать) **и** нельзя допустить, чтобы команда прошла, а факт её выполнения не сохранился (иначе аудит бесполезен как раз там, где важнее всего). В проекте уже есть готовый архитектурный паттерн именно для этого компромисса — `EventBus`/`EventSink` (`runtime/event_sink.py`) — асинхронная, развязанная запись, не блокирующая обработку кадра. Аудит действий пользователя должен писаться по тому же принципу (fire-and-forget с логированием сбоя записи, а не try/except, проглатывающий и ошибку, и попытку), а не как `INSERT ... ; COMMIT` внутри того же request-обработчика, что дёргает реле.

**Как избежать (сводно):**
- Явно решить объём журнала на этапе проектирования: включает ли он неуспешные попытки (логин, 403) — рекомендация: да, отдельным типом события, раз это система контроля доступа.
- Redaction-фильтр на запись аудита — те же поля, что уже редактируются в API-ответах и логах (`channels.source`, `controllers.password`), выносится в общую функцию, переиспользуемую и там, и там.
- Ретеншн журнала действий через существующий `DataLifecycleService`, не новый механизм.
- Асинхронная/развязанная запись для действий, критичных по задержке (в первую очередь — команды на контроллеры), по образцу `EventSink`.

**Признаки проблемы:**
В таблице `audit_log`/`user_actions` находится полный JSON payload PUT-запроса на канал/контроллер; нет `retention_days` для этой таблицы в `config/registry.py`; ручной тест «оборвать соединение с БД во время срабатывания реле» ломает открытие ворот, а не только запись в журнал.

**Фаза:** журнал действий — отдельная фаза; зависит от фазы retention (переиспользование `DataLifecycleService`) и от решения по асинхронной записи, которое стоит зафиксировать раньше самого журнала (архитектурное решение, а не деталь реализации).

### Ошибка 9: Неоднозначность Просмотр/Изменение/Удаление для действий, которые не являются CRUD

**В чём проявляется:**
Модель прав `PROJECT.md` описана в терминах Просмотр/Изменение/Удаление по разделам (Наблюдение, Журнал, Зоны, Клиенты, Настройки) — естественно для CRUD-сущностей (создать зону, изменить клиента, удалить список), но в системе есть действия, которые не укладываются в этот CRUD-словарь однозначно:

- **Старт/стоп канала** (`runtime/channel_runtime.py`, `ChannelProcessor`) — это не изменение конфигурации канала (записи в `channels` не меняются), а изменение runtime-состояния. Это «Изменение»? Или отдельное действие, не покрываемое тремя галочками вообще?
- **Ручное срабатывание реле** (`controller_service.send_command(..., reason="api-test")`, сегодня — `controllers.py:58`, `require_role("superadmin")`) — это использование оборудования, а не настройка контроллера. `PROJECT.md` сам явно ставит это под вопрос как открытый пункт исследования («как разграничивать «настройку» и «использование» контроллеров... изучить подходы аналогов (Trassir/AutoTrassir)... принять решение до реализации»). Сегодня в коде такого разделения нет вообще — единственный эндпоинт, дёргающий `send_command`, защищён `require_role("superadmin")` целиком, то есть для операторского «горячего» открытия шлагбара по кнопке в UI просто нет подходящего под текущую модель эндпоинта.
- **Экспорт/бэкап/восстановление БД** — это «Просмотр» данных Журнала (экспорт событий) или отдельная операция уровня «Настройки» (сегодня и то, и другое защищено `tab:settings`, что уже отмечено как архитектурный дефект в `CONCERNS.md`)?

**Почему это опасно оставить неявным:**
Если каждый разработчик решает «на глазок», при переносе на новую модель один свяжет старт/стоп канала с `Наблюдение:Изменение`, другой — с `Настройки:Изменение` (раз конфигурация канала лежит в «Настройках» сегодня), и получится расхождение между тем, что разработчик считал очевидным, и тем, что администратор увидит в UI как смысл галочки.

**Как избежать:**
- Прежде чем присваивать permission-строки конкретным эндпоинтам, составить **явную таблицу «действие → раздел → уровень (Просмотр/Изменение/Удаление)»** как часть дизайна (не как побочный продукт кода) — одну на весь бэкенд, а не решение по каждому PR отдельно. Она же становится источником для `AVAILABLE_PERMISSIONS`/каталога прав (см. Ошибку 11).
- Закрыть открытый пункт `PROJECT.md` про «использование vs настройка» контроллеров **до** того, как писать guard на эндпоинт ручного срабатывания реле — иначе он неизбежно попадёт в `Настройки` по инерции (как сегодняшний `test_controller`), что для «горячей кнопки открыть ворота» оператору неудобно и концептуально неверно (это не настройка).
- Стартовая рекомендация (не решение, гипотеза к проверке): «изменение runtime-состояния без изменения хранимой конфигурации» (старт/стоп канала, ручной триггер реле) — трактовать как действие уровня «Изменение» того раздела, которому принадлежит объект (Наблюдение — для канала, отдельная категория «Контроллеры» — для реле, если она появится), а не автоматически «Настройки», просто потому что кнопка физически лежит на странице настроек сегодня.

**Признаки проблемы:**
В таблице соответствий (если она есть) нет строки для `start_channel`/`stop_channel`/`trigger_relay`; в PR добавляется guard на новый эндпоинт без ссылки на эту таблицу, «по аналогии с соседним эндпоинтом».

**Фаза:** проектирование каталога прав, до реализации — прямо соответствует пункту `PROJECT.md` «Исследование… принять решение до реализации».

### Ошибка 10: Утечка спецлогики superadmin в обычные хендлеры вместо централизованной проверки (уже произошло один раз в этом коде)

**В чём проявляется:**
`require_permission()` (`app/api/deps.py:66`) уже централизует обход для superadmin (`if current_user.get("role") == "superadmin": return current_user`) — это правильное место для такой логики: одна точка. Но `change_password()` (`app/api/routers/users.py:142`) не использует эту зависимость, а **вручную дублирует** ту же проверку прямо в теле хендлера: `current_user["role"] == "superadmin" or "tab:settings" in current_user.get("permissions", [])`. Это уже задокументировано как известный дефект (`AGENTS.md`: «`change_password` tests `"tab:settings" in permissions` inline in the handler body»).

**Почему это опасно масштабировать:**
При переходе на произвольные роли с галочками таких мест — «в основном не superadmin/не чужие данные, но с исключением для себя» (`change_password`, будущие аналоги: пользователь редактирует собственный профиль, видит собственные действия в журнале) — станет больше, а не меньше. Если паттерн «дописать проверку прямо в хендлере» не остановить сейчас, каждое такое место будет проверять `role == "superadmin"` или использовать свой набор строковых литералов прав, и логика авторизации расползётся по 10 файлам вместо одного модуля.

**Как избежать:**
Один раз добавить в `app/api/deps.py` недостающий примитив — `require_permission_or_self(permission)` (или эквивалент под новую модель: `require_access_or_self(level)`) — фабрику зависимости для случая «сам себе можно, или есть право X», и переписать `change_password` на него в рамках этой же фазы (не «когда-нибудь потом» — иначе это второй экземпляр той самой проблемы, которую фаза должна устранить, переживёт саму фазу).

**Признаки проблемы:**
`grep -rn 'role.*superadmin.*or\|"tab:' app/api/routers/` находит булеву проверку прав внутри тела хендлера, а не в `Depends(...)`.

**Фаза:** backend-применение прав — включить рефактор `change_password` явным пунктом плана, не побочным эффектом.

### Ошибка 11: Расхождение каталога прав между бэкендом и фронтендом

**В чём проявляется:**
Сегодня список прав для UI управления пользователями — `AVAILABLE_PERMISSIONS` (`app/api/routers/auth.py:25`), захардкоженный список из 5 `tab:*`-записей, физически отделённый от:
- `_OPERATOR_FORBIDDEN_PERMISSIONS` (`app/api/routers/users.py:19`) — ещё один захардкоженный набор, знающий про роль `operator` по имени;
- реальных строковых литералов `"tab:settings"`, разбросанных по `require_permission("tab:settings")` в 18 местах разных роутеров — это и есть тот самый «зафиксированный инвариант: 18 мест», который `AGENTS.md` прямо называет подлежащим замене этим циклом.

При переходе на 5 разделов × 3 действия (до 15 leaf-прав, при этом «Настройки» в этом цикле — одна галочка на раздел, то есть меньше) риск тот же, но острее: каталог, который видит администратор в UI редактора ролей, должен быть математически тем же множеством строк, которое проверяют `require_*`-зависимости в роутерах — иначе либо в UI есть галочка, которая ничего не защищает (мёртвое право), либо в коде есть проверка права, которого нет в UI (недостижимая галочка — никто не может выдать это право через интерфейс).

**Как избежать:**
Единый модуль (например, `app/api/permissions.py`) с константами раздел×действие, из которого одновременно: (а) строится ответ `/api/permissions/available` для фронтенда, (б) импортируются литералы во всех `require_access`/`require_permission` вызовах в роутерах — не строковые литералы «на месте». Тест, перечисляющий все вызовы `require_permission(...)`/`require_access(...)` в `app/api/routers/` (через AST или через сам импорт роутеров и инспекцию `app.routes`) и сверяющий использованные строки с каталогом — в обе стороны (нет использованных вне каталога, нет каталожных, что нигде не используются).
Заменить (не расширять) инвариант «tab:settings ровно в 18 местах» из `tests/test_permission_guards.py` на инвариант «каждое использование строки права взято из каталога» — это и есть предписанная задача этого цикла (`AGENTS.md`: «...will intentionally replace»), а не просто разрешение поднять счётчик.

**Признаки проблемы:**
`grep -rn '"tab:' app/api/routers/` и содержимое `AVAILABLE_PERMISSIONS` дают разные множества строк; в UI редактора ролей есть галочка, клик по которой не блокирует и не открывает ни один реальный эндпоинт.

**Фаза:** проектирование каталога прав → backend-применение прав; тест-инвариант — в той же фазе, что и сама замена `tab:settings`.

### Ошибка 12: Тестовое покрытие — юнит-тесты зависимостей вместо сквозной проверки маршрутов

**В чём проявляется:**
Существующий `tests/test_permission_guards.py` — качественный, но структурно ограниченный паттерн: он вызывает `require_role(...)`/`require_permission(...)` напрямую с руками собранным `dict` пользователя (`_superadmin_user()`, `_operator_user()`), минуя FastAPI целиком, плюс несколько `assert "require_permission" in src` на текст файла. Это проверяет, что *сама функция-guard* работает корректно на выдуманных входах — но не проверяет, что *конкретный маршрут* её действительно вызывает, ни тем более что маршрут ведёт себя правильно для реального (не сфабрикованного) пользователя, включая пограничные случаи из этого документа: заблокированный пользователь, самоблокировка, роль без права, но с похожим названием, переоткрытое SSE-соединение после блокировки.
`.planning/codebase/CONCERNS.md` уже фиксирует это как «Test Coverage Gaps → Destructive Operations Not Tested for Authorization», Priority: High.

**Как избежать:**
Для этого цикла — обязательные категории тестов, которых сегодня нет ни одной:
1. Параметризованный тест по всем зарегистрированным маршрутам (`app.routes`), сверяющий каждый со списком ожидаемых уровней доступа (реализует Ошибку 2 как тест, не только как процесс).
2. Для каждого раздела — тест «пользователь с ролью, имеющей только Просмотр, получает 403 на Изменение/Удаление того же раздела» и «пользователь без права раздела вообще получает 403 на Просмотр» — через реальный `TestClient`, не через прямой вызов dependency-функции, чтобы поймать случаи вида Ошибки 1 (забыли навесить `Depends` вообще).
3. Блокировка пользователя с активным токеном → следующий запрос (любой, не только `/api/auth/me`) отклоняется — этот тест уже возможен благодаря архитектуре из Ошибки 4 (БД — источник истины), но сегодня не написан.
4. Хотя бы один тест на self-lock сценарии из Ошибки 5/6 (самоблокировка через смену роли, удаление роли в использовании).
5. Замена/переписывание `TestRouterImports` (грепа по исходникам) на структурную проверку через `app.routes`.

**Признаки проблемы:**
`pytest --collect-only tests/test_permission_guards.py` показывает тесты, названные по роутерам, которых в реальности 12+, а не 5; ни один тест не создаёт `TestClient` и не делает реальный HTTP-запрос к защищённому маршруту.

**Фаза:** сквозная — тесты пишутся в каждой фазе, где меняется соответствующий контракт (backend-применение прав, блокировка/сессии, журнал действий), а не одним отдельным «тестовым» тикетом в конце цикла.

## Паттерны технического долга

| Сокращение пути | Немедленная выгода | Долгосрочная цена | Когда приемлемо |
|---|---|---|---|
| Оставить `tab:settings` временно ещё в паре новых мест «пока не готова новая модель» | Быстрее закрыть смежную задачу | Счётчик инвариантов растёт именно тогда, когда цикл должен его гасить — путает объём миграции | Никогда в рамках этого цикла — `AGENTS.md` явно фиксирует 18 как замораживаемое число до замены |
| Кэшировать права в JWT «для производительности» | Меньше запросов к БД на каждый HTTP-вызов | Ломает «применяется сразу, без перевхода» — прямое требование `PROJECT.md` | Только если добавлена активная инвалидация кеша при любом изменении роли/блокировке — тогда это не сокращение, а отдельная фича |
| Синхронная запись в audit_log в той же транзакции, что action | Проще писать, гарантия «залогировано, если действие прошло» | Отказ БД/пула блокирует или замедляет действия с физическим оборудованием (реле) | Разве что для некритичных по задержке действий (изменение зоны, клиента) — не для команд на контроллер |
| Один общий permission `"settings"` без разбора на пользователей/роли/бэкап/ретеншн | Меньше кода в этом цикле, соответствует решению владельца не дробить «Настройки» сейчас | Любой с `Настройки:Изменение` — де-факто root; эскалация (Ошибка 6) | Приемлемо в этом цикле по явному решению владельца, но должно быть задокументировано как принятый риск, не как забытая деталь |
| Ручная булева проверка прав в теле хендлера вместо `Depends` | Быстро закрыть один частный случай («сам себе можно») | Логика авторизации расползается по файлам, второй такой случай останется незамеченным | Никогда — есть один прецедент (`change_password`), увеличивать их число нельзя |

## Интеграционные подводные камни

| Точка интеграции | Типичная ошибка | Правильный подход |
|---|---|---|
| SSE (`/api/events/stream`) | Проверить токен один раз на handshake, дальше доверять открытому соединению до истечения `proxy_read_timeout 1h` | Периодическая ре-проверка пользователя внутри генератора (см. Ошибку 3), синхронно с уже существующим `ping`-циклом |
| MJPEG (`/api/channels/{id}/preview.mjpg`) | Та же проблема, что SSE, плюс токен в query-string виден в nginx access-логе | То же решение + отдельный короткоживущий stream-токен вместо основного JWT в URL |
| Контроллеры реле (`controller_service.send_command`) | Синхронная запись аудита в одной транзакции с физической командой; отсутствие разделения «настройка контроллера» / «разовое срабатывание» | Асинхронная запись аудита по образцу `EventSink`; явная permission-таблица действие→раздел до реализации ручного триггера (Ошибка 9) |
| Экспорт/бэкап БД (`data.py`) | Всё ещё под `tab:settings` (P18) — при переносе на новую модель легко снова свалить «экспорт Журнала» и «бэкап всей БД» в одну галочку, хотя это разные владельцы данных | Развести по владельцу данных (Журнал-экспорт → раздел «Журнал»; бэкап/восстановление БД → отдельная административная категория, не «Настройки: Изменение» по инерции) |

## Ловушки производительности

| Ловушка | Симптомы | Профилактика | Когда проявляется |
|---|---|---|---|
| `audit_log`/`user_actions` без ретеншна | Таблица растёт быстрее `events` (действий пользователей может быть на порядок больше при активной работе с ролями/каналами) | Подключить к существующему `DataLifecycleService`/retention worker с самого начала, не добавлять отдельно | С первых месяцев эксплуатации при активном администрировании |
| Перечитывание пользователя из БД на каждый запрос (уже так сегодня) | Дополнительный SELECT на каждый HTTP-вызов | Это осознанная цена за немедленное применение блокировки/прав (Ошибка 4) — не оптимизировать без инвалидации | При очень высокой частоте запросов (много одновременных SSE/MJPEG-клиентов) — тогда профилировать, не гадать |
| Периодическая ре-проверка прав внутри SSE/MJPEG-генератора слишком частая | Лишняя нагрузка на пул соединений (`min=2, max=10` — и так тесный лимит, см. `CONCERNS.md`) | Интервал ре-проверки сопоставим с существующим ping-интервалом (15 с для SSE), не чаще | При десятках одновременных потоковых клиентов на десяти доступных соединениях пула |

## Ошибки безопасности

| Ошибка | Риск | Профилактика |
|---|---|---|
| Токен в query-string SSE/MJPEG попадает в nginx access-лог и `Referer` | Кража долгоживущего токена из лога/прокси даёт полный доступ к API под личностью жертвы | Короткоживущий отдельный stream-токен для media/SSE; кастомный `log_format` без query-string для этих путей |
| Аудит-лог хранит несекретированные `channels.source`/`controllers.password` | Более широкая аудитория (администраторы с правом на журнал), чем узкий круг, видящий текстовые логи контейнера | Redaction на границе записи, общая функция с уже существующей практикой редактирования этих полей в API-ответах |
| Право «Настройки: Изменение» = де-факто root без предупреждения | Администратор выдаёт «немного прав» и не осознаёт, что выдал полный контроль | Явная документация + минимум self-edit guard (Ошибка 6) |
| Дефолтные `admin`/`operator` без принуждения к смене пароля, физический доступ на кону | Компрометация дефолтного пароля = открытие шлагбаума посторонним | Постоянный UI-баннер + событие в аудит-логе при входе под дефолтным паролем (расширение уже существующего `warn_default_password`) |
| Ручное дублирование `role == "superadmin"` проверок в хендлерах вместо `Depends` | Один пропущенный кейс — дыра, которую сложно найти грепом, так как логика не единообразна | Централизация через `require_permission_or_self`/эквивалент, запрет на инлайн-проверки в код-ревью |

## UX-ошибки

| Ошибка | Как страдает пользователь | Что делать вместо этого |
|---|---|---|
| Предупреждение о дефолтном пароле — одноразовый тост при логине | Легко закрыть и забыть; спустя месяцы никто не помнит, что пароль не менялся | Постоянный баннер до смены пароля + видимость в аудит-логе для администратора, а не только для самого пользователя |
| 403 без объяснения, какого именно права не хватает | Администратор не понимает, какую галочку добавить пользователю | Сообщение об ошибке или UI-подсказка называют конкретный раздел+действие (например, «требуется право Изменение раздела Контроллеры»), не просто «Недостаточно прав» |
| Удаление роли, назначенной пользователям, без предупреждения | Пользователи неожиданно теряют доступ без объяснения после действия администратора в другом месте UI | При попытке удалить роль — явное предупреждение с числом затронутых пользователей до подтверждения |
| Самоблокировка через смену собственной роли без предупреждения | Администратор случайно теряет доступ к панели управления пользователями и должен вспоминать про superadmin | Явное предупреждение в UI до сохранения: «это изменение лишит вас доступа к управлению пользователями» |

## Чек-лист «выглядит готовым, но не готово»

- [ ] **Права по разделам:** каждый маршрут в `app/api/routers/` проверен на наличие `require_access`/`require_permission` — проверить структурным тестом по `app.routes`, не визуальным просмотром файлов
- [ ] **Блокировка пользователя:** проверено не только через `/api/auth/me`, а хотя бы через один эндпоинт каждого раздела (Наблюдение/Журнал/Зоны/Клиенты/Настройки) — включая SSE/MJPEG с уже открытым соединением
- [ ] **Немедленное применение прав:** протестирована смена роли у уже вошедшего пользователя без re-login — не только теоретически «БД — источник истины», а end-to-end тестом с реальным HTTP-запросом до и после изменения
- [ ] **Журнал действий:** проверено, что записи не содержат `channels.source`/`controllers.password` целиком — ручной просмотр нескольких записей после операций с каналами/контроллерами
- [ ] **Журнал действий:** проверено поведение при недоступности БД во время команды на контроллер — физическое действие (реле) не заблокировано отказом записи аудита
- [ ] **Дефолтные пользователи:** `admin`/`operator` дают предупреждение о дефолтном пароле так же, как сегодня superadmin — не только при первом входе, но и при последующих, пока пароль не изменён
- [ ] **Каталог прав:** множество строк, используемых в `require_*`-вызовах, совпадает 1:1 с тем, что отдаёт `/api/permissions/available` — автоматической проверкой, не вручную
- [ ] **Self-lock:** попытка администратора лишить себя права управления пользователями/ролями (через смену роли, не только деактивацию) — заблокирована или явно предупреждена

## Стратегии восстановления

| Ошибка | Стоимость восстановления | Шаги |
|---|---|---|
| Обнаружен забытый незащищённый эндпоинт в проде | LOW | Добавить `Depends(require_access(...))`, задеплоить; исторические вызовы этого эндпоинта проверить по текстовым логам (если пишутся) на предмет злоупотребления |
| Обнаружена самоблокировка администратора (никто не может управлять ролями) | LOW | Вход через technical superadmin (`.env` `SUPERADMIN_PASSWORD`) — по дизайну именно для этого крайнего случая, доступ есть всегда |
| Утечка токена через query-string в логах nginx | MEDIUM | Ротация `JWT_SECRET_KEY` инвалидирует все токены разом (все пользователи вынуждены перелогиниться) — приемлемо как реакция на инцидент; отдельно — очистка исторических логов nginx |
| Обнаружено, что audit_log хранил секреты в открытом виде | MEDIUM–HIGH | Смена скомпрометированных учётных данных (пароли контроллеров, при возможности — RTSP-креды камер), очистка/redaction исторических записей журнала, не только исправление кода вперёд |
| Роль удалена, пользователи остались без доступа | LOW | Пересоздать роль с теми же правами и переназначить — если это единственная управляющая роль и её некому пересоздать штатно, тот же путь через superadmin |

## Соответствие ошибок фазам

| Ошибка | Фаза | Как проверить, что закрыта |
|---|---|---|
| 1. Открытые API под видимостью вкладок | Backend-применение прав | Структурный тест по `app.routes`: 0 маршрутов без явного уровня доступа |
| 2. Забытые эндпоинты при миграции | Backend-применение прав | Тот же структурный тест — падает при добавлении нового незащищённого маршрута в будущем |
| 3. SSE/MJPEG/медиа обходят проверку | Backend-применение прав (отдельная задача) | Тест: блокировка пользователя с открытым SSE/MJPEG-соединением → поток закрывается в пределах интервала ре-проверки |
| 4. Протухшие JWT-claims (регресс) | Проектирование схемы ролей/прав (ADR/ограничение) | Код-ревью: ни один PR не кладёт права в JWT и не кеширует их без инвалидации |
| 5. Lockout (роли, самоблокировка) | CRUD ролей + Backend-применение прав | Тесты: удаление роли в использовании → 409; смена своей роли, лишающая прав управления, → блокировка/предупреждение |
| 6. Эскалация через себя | CRUD ролей (минимум); дробление «Настроек» (полное решение, backlog) | Тест: нельзя редактировать роль, назначенную самому себе |
| 7. Дефолтные `admin`/`operator` | Seed-пользователи + Журнал действий (совместно) | `warn_default_password` работает для всех, не только superadmin; вход под дефолтным паролем виден в журнале |
| 8. Дыры в журнале действий | Журнал действий (зависит от фазы retention) | Redaction, retention, async-запись — каждая проверена отдельным тестом/ручным сценарием |
| 9. Неоднозначность Просмотр/Изменение/Удаление | Проектирование каталога прав, до реализации | Таблица «действие→раздел→уровень» существует и на неё ссылается каждый PR, добавляющий guard |
| 10. Утечка superadmin-логики в хендлеры | Backend-применение прав | `change_password` переписан на общий примитив; 0 инлайн-проверок `role == "superadmin"` в теле хендлеров |
| 11. Расхождение каталога прав backend/frontend | Проектирование каталога прав → Backend-применение прав | Тест сверяет множество строк прав в роутерах с каталогом в обе стороны |
| 12. Недостаточное тестовое покрытие | Сквозная, по каждой фазе | Каждая фаза добавляет `TestClient`-тесты для своих новых эндпоинтов, не только dependency-юнит-тесты |
