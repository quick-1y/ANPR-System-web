# Requirements: Web ANPR System — Роли, пользователи и права доступа

**Defined:** 2026-09-24
**Core Value:** Администратор может гибко выдать любому пользователю ровно те доступы, которые нужны, через роли с галочками, и сервер реально соблюдает эти права, а не только скрывает вкладки.

## v1 Requirements

### Каталог прав и серверная проверка (PERM)

- [ ] **PERM-01**: В коде существует единый каталог прав: разделы Наблюдение, Журнал, Зоны, Клиенты, Настройки × действия Просмотр / Изменение / Удаление, плюс отдельное право «Ручное управление реле». Каталог — единственный источник для серверных проверок, API ролей и видимости вкладок во фронтенде
- [ ] **PERM-02**: Каждый API-эндпоинт явно объявляет требуемое право (раздел + действие) либо явный уровень (публичный, «только свой аккаунт», только superadmin); тест перебирает все маршруты приложения и падает на эндпоинте без объявления
- [ ] **PERM-03**: Пользователь без права «Просмотр» на раздел не видит вкладку, а сервер отвечает 403 на чтение данных этого раздела (включая медиа и потоки)
- [ ] **PERM-04**: Пользователь без права «Изменение» на раздел получает 403 на создание и изменение объектов этого раздела
- [ ] **PERM-05**: Пользователь без права «Удаление» на раздел получает 403 на удаление объектов этого раздела
- [ ] **PERM-06**: Ручное срабатывание реле/шлагбаума (хоткей, кнопка) разрешено только при отдельной галочке «Ручное управление реле»; добавление, изменение и удаление контроллеров — права раздела «Настройки»
- [ ] **PERM-07**: Управление пользователями и ролями закрыто правами раздела «Настройки» (Просмотр — видеть, Изменение — создавать/менять, Удаление — удалять)
- [ ] **PERM-08**: Смена собственного пароля и личные настройки интерфейса не требуют никаких прав раздела
- [ ] **PERM-09**: Старая модель удалена целиком: `users.permissions` JSONB, права `tab:*`, `require_permission("tab:settings")`, `require_role(...)` для обычных пользователей, проверка `tab:settings` внутри `change_password`

### Роли (ROLE)

- [ ] **ROLE-01**: Администратор может создать роль с произвольным названием и любым набором галочек
- [ ] **ROLE-02**: Администратор может переименовать роль и изменить её галочки
- [ ] **ROLE-03**: Администратор может удалить роль; роль, назначенную хотя бы одному пользователю, удалить нельзя (понятное сообщение об ошибке)
- [ ] **ROLE-04**: Список ролей показывает название, отмеченные права и число пользователей с этой ролью
- [ ] **ROLE-05**: Названия ролей не несут никакой логики — любая роль, включая «Администратор» и «Оператор», редактируется и удаляется наравне с остальными

### Пользователи (USER)

- [ ] **USER-01**: Администратор может создать пользователя с логином, паролем, ФИО и одной ролью
- [ ] **USER-02**: Администратор может изменить ФИО и роль пользователя; одну роль можно назначить любому числу пользователей
- [ ] **USER-03**: Администратор может задать новый пароль другому пользователю; любой пользователь может сменить свой пароль
- [ ] **USER-04**: Администратор может заблокировать и разблокировать пользователя без удаления; заблокированный не может войти, а его уже открытая сессия теряет доступ со следующего запроса
- [ ] **USER-05**: Администратор может удалить пользователя
- [ ] **USER-06**: Список пользователей показывает логин, ФИО, роль, статус (активен/заблокирован) и время последнего входа
- [ ] **USER-07**: Изменение роли пользователя или галочек роли действует для уже вошедших пользователей со следующего запроса, без перевхода

### Развёртывание и superadmin (BOOT)

- [ ] **BOOT-01**: На чистой БД автоматически создаются роли «Администратор» (все права, включая ручное управление реле) и «Оператор» (Просмотр на Наблюдение и Зоны + «Ручное управление реле»)
- [ ] **BOOT-02**: На чистой БД автоматически создаются пользователи `admin` (роль «Администратор») и `operator` (роль «Оператор») с паролями по умолчанию, указанными в документации; смена пароля не принуждается; повторный запуск не пересоздаёт и не перезаписывает их
- [ ] **BOOT-03**: superadmin (из `.env`) имеет все права, единственный видит раздел «Разработка», не отображается в списке пользователей и может создать первого администратора
- [ ] **BOOT-04**: Действия superadmin не записываются в журнал действий

### Журнал действий (AUDIT)

- [ ] **AUDIT-01**: Каждое изменяющее действие пользователя (создание/изменение/удаление/блокировка пользователей и ролей, каналов, зон, списков, клиентов, контроллеров, настроек; старт/стоп канала; ручное срабатывание реле; экспорт, бэкап, восстановление, ручной запуск retention) записывается: время, логин и ФИО на момент действия, действие, объект, результат
- [ ] **AUDIT-02**: Записываются входы в систему — успешные и неудачные
- [ ] **AUDIT-03**: В журнал никогда не попадают секреты: пароли и их хеши, RTSP-адреса с учётными данными, пароли контроллеров
- [ ] **AUDIT-04**: Пользователь с правом «Просмотр» на «Настройки» видит журнал действий в интерфейсе: новые записи сверху, постранично
- [ ] **AUDIT-05**: Сбой записи в журнал не ломает и не отменяет само действие (в частности, открытие шлагбаума)
- [ ] **AUDIT-06**: Старые записи журнала удаляются retention-воркером по отдельно настраиваемому сроку хранения

### Потоки (STRM)

- [ ] **STRM-01**: Открытый поток событий (SSE) периодически перепроверяет пользователя и закрывается, если его заблокировали или он потерял право на просмотр
- [ ] **STRM-02**: Открытое MJPEG-превью канала периодически перепроверяет пользователя и закрывается при блокировке или потере права на Наблюдение
- [ ] **STRM-03**: Токен доступа из query-string потоков не попадает в access-лог nginx

### Интерфейс (UI)

- [ ] **UI-01**: Экран ролей: список ролей и форма с матрицей галочек (раздел × Просмотр/Изменение/Удаление + «Ручное управление реле»)
- [ ] **UI-02**: Экран пользователей: список, создание, редактирование ФИО/роли/пароля, блокировка/разблокировка, удаление
- [ ] **UI-03**: Вкладки меню видны только при праве «Просмотр»; кнопки изменения и удаления скрыты или недоступны без соответствующего права
- [ ] **UI-04**: Кнопка и хоткей ручного управления реле доступны только при галочке «Ручное управление реле»
- [ ] **UI-05**: Экран журнала действий
- [ ] **UI-06**: После изменения прав интерфейс уже вошедшего пользователя отражает новые права без перевхода (например, при следующем обновлении данных о текущем пользователе)

### Документация (DOC)

- [ ] **DOC-01**: README, `docs/technical/` (модель прав, эндпоинты, схема БД) и `docs/guides/` (администратор: роли и пользователи, пароли по умолчанию) обновлены на русском; раздел авторизации в `AGENTS.md` отражает новую модель

## v2 Requirements

### Безопасность управления

- **SAFE-01**: Нельзя удалить или заблокировать последнего пользователя с правами управления пользователями
- **SAFE-02**: Пользователь не может снять права с самого себя или заблокировать себя
- **SAFE-03**: Отдельное право «Пользователи и роли», не входящее в «Настройки» (защита от самоэскалации)

### Журнал действий

- **AUDIT-07**: Фильтры журнала по пользователю, дате и типу действия
- **AUDIT-08**: Экспорт журнала действий в CSV

### Детализация прав

- **GRAN-01**: Дробление «Настроек» на подразделы с отдельными галочками (каналы, контроллеры, пользователи, данные, общие)
- **GRAN-02**: Ограничение роли по конкретным каналам/камерам и контроллерам

## Out of Scope

| Feature | Reason |
|---------|--------|
| Несколько ролей на пользователя | Решение владельца: одна роль; при необходимости создаётся новая роль-надмножество |
| Миграция существующих пользователей и полей `role`/`permissions` | Политика проекта: чистая схема, откат через Git |
| Принудительная смена пароля по умолчанию | Решение владельца |
| Политика сложности/ротации паролей | Не соответствует масштабу on-prem инсталляции |
| LDAP/AD/SSO | Несоразмерный объём для одного объекта |
| Мгновенный «выкинуть сессию» с хранилищем отзыва токенов | Нет Redis/session store; проверка на каждый запрос даёт тот же эффект |
| Права по расписанию / временные роли | Не запрошено |
| Серверные персональные предпочтения | Личное состояние UI остаётся в `localStorage` |
